# 提成关系与计算

订单台提供店铺、宝贝链接、ERP SKU、订单与售后事实。台账拥有人员身份、关系有效期、分点、计算口径和结算结果。

## 时间与版本

- 人员关系使用北京时间的 `[valid_from, valid_to)` 区间；同一店铺、宝贝的区间不能重叠。
- 关系一版包含完整时间线及各时间段全部分点人员。草稿不会影响计算，发布后保留旧版本。
- 计算口径按账期月份生效，可全公司设置，也可逐店覆盖。它与订单权益时间分开。
- 终止关系会新增待确认或明确不提成的时间段，不删除历史，不恢复更旧的人员，也不自动转店铺兜底。
- 已结账财务run仍是展示依据。关系变更生成新的计算/调整试算，不改冻结run。

## 身份与匹配

主键是台账店铺ID与平台宝贝ID；ERP SKU保留给成本侧使用，不可替代缺失宝贝ID。人员用独立ID识别，同名不自动合并。ERP账号只做可选外部映射。

店铺默认关系的宝贝ID使用 `*`。明确0%与未配置分开。缺订单时间、宝贝ID、人员关系或已到期的订单保留为待分配。

`order_feed.py`把集成API的字段转换成快照契约，包括商品ID/名称、平台子单ID、下单与付款时间。未确认店铺的事件仍被持久保存，但不进入已确认店铺的账簿。重算队列持久化；同步时使用本轮捕获的源序号作为追赶目标。

## 明细与精度

每个订单、每个人先合并其多个角色的点数，再使用Decimal计算并按ROUND_HALF_UP取整到分。所有人员、商品与店期合计均来自明细相加。

明细保留财务run、原订单/子单、宝贝、权益时间、记账月份、人员ID、角色分项、关系版本、口径版本、原基数、亏损处理和金额。关系、口径及计算元数据禁止通过应用更新或删除；明细文件按SHA256读取校验。

财务基数未齐或与损益节点不符时标记试算。涉及工资的关系由口径决定暂不计算，或先不扣工资试算；不能把未提供的工资当作已确认的零成本。

## 迁移与复核

历史Excel的五组人员列使用完整表头匹配。原文件按SHA留存，所有工作表记录概况，每个主表数据行保留原始字段与行号。重复按店铺与宝贝分组；完全相同的组不重复生效，矛盾组保留待确认。

迁移分为上传核查、启用合格组、逐条复核。无法确认的店铺、占位ID、人员标签、缺点数与同组冲突不能自动启用。复核界面可登记修正关系，原始行不改写；调整原因、操作人及新版本被同时保存。

## 运行与管理

数据目录为 `LEDGER_HOME/commission/`，包含 `registry.db`、原始导入文件和计算Parquet。该目录必须随台账备份；不要只备份代码或CSV。

新模块路径为 `/#/commission`，旧版页面保留为 `/#/commission/legacy`。新关系启用后，旧CSV写接口禁止继续修改提成，避免绕过版本与审计。

日常页面只显示店铺、商品宝贝、状态、所属人员和提成比率。在同一个编辑框中选择或输入姓名、调整比例并保存即可，无需单独登录，也不必进入人员、迁移、口径或版本页面。生效时间和修改记录折叠在该商品的编辑框内。

默认采用内网直接编辑模式，后台记录为“本机操作”，不把它伪称为某个具体人员的操作。已有财务口径及审计历史保留。若以后确实需要独立账号，可设置 `LEDGER_COMMISSION_AUTH_MODE=password` 并通过受保护的密码文件初始化：

```text
python -m ledger.commission_cli --home <工作区> operator-add <账号> --password-file <密码文件> --admin
```

若公司明确选择只登记姓名，可设置 `LEDGER_COMMISSION_AUTH_MODE=declared`；事件会以 `declared:` 标记，这种方式不能证明操作人身份。

命令行支持目录同步、原表核查、启用合格组与计算口径发布。每个写命令要求可识别操作者与原因，输出不包含密码。常用命令：

```text
python -m ledger.commission_cli catalog-sync
python -m ledger.commission_cli stage <原表.xlsx> --effective-from <日期> --by <操作者>
python -m ledger.commission_cli activate <批次ID> --by <操作者> --reason <原因>
python -m ledger.commission_cli policy-set --effective-from <月份首日> --base net_profit --wages skip_preview --by <操作者> --reason <原因>
```

管理API位于 `/api/commission-v2`：人员、商品目录、关系草稿/发布/终止/恢复、批量修改、导入复核、口径、逐单明细及导出。表格导出保留长ID，防止Excel按数字缩短；操作日志导出包含修改前后值。

## 发布检查

发布仅替换台账代码与静态资源，不覆盖线上模型、原表、数据库、订单侧或已结账数据。发布前备份覆盖文件并核对旧版本，失败回滚代码。发布后检查新API、目录、消费进度、关系数量、账期基数、逐单加总、明细下载与关闭账期的原run指针。


## 日常批量操作

提成页使用自己的店铺与人员筛选，切店时立即更新列表。可逐项跨店勾选，也可选择筛选内全部可设置商品并排除个别项。

“批量设置”提供统一替换、只调整指定人员且保留其他人、移除指定人员三种方式。“批量新增”支持多家店铺和多行宝贝ID。两者均先展示店铺、商品、原分配、新分配及生效时间，再一次保存；重复点击不会重复生效，任一项发生冲突则整批不保存。

“人员名单”统一新增或改名、修改工号，并显示当前覆盖店铺和宝贝数；“查看分配”直接回到按该人员筛选的商品列表。

“Excel导入”使用页面下载的xlsx模板，每行一个人员，同店同宝贝同时间的多行自动组合。支持多个数据sheet；明确命名的说明和示例sheet不导入。长ID须为文本，百分比推荐明确填写5%等格式。上传只生成预览，确认后才写入关系。批次及源文件保存在commission目录，随工作区备份。
