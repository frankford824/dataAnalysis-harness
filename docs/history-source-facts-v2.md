`history_cost_source_facts.v2` 是独立的可信来源事实规则，必须由已登录人员批准具体店月和有效期，默认自动化开关仍关闭。既有 v1 的授权、逐单到分检查和人工两位小数接口不变。v2 不写人工成本补录表，不接受模型提供的金额、单价、数量、日期或源 URL。

服务接口 `POST /api/automation/service-facts` 使用现有 `approved_action` 服务身份，仅接受：

```json
{"request_id":"batch-reference","rule_id":"history_cost_source_facts.v2","case_id":"current-case","store_id":"store","period":"2026-06","run_id":1,"input_sha":"current-input-sha","items":[{"coverage_key":"sealed-gap","context_sha":"sealed-context","expected_line_revision":0}]}
```

同一批最多 100 个当前缺口，固定同店、同月、同 run/input。后端重读原 ERP 成员和历史报价，核对 confirmed 店铺映射、平台父/子单、内部成员、SKU、公司、原始日、原数量及正常组件单位。相同 SKU/公司/原日的报价在批内复用；来源失效不重复访问同一已失败客户端。原始报价字节、SHA、区间、原数量、原单价与来源引用留在本机。

成功时，一个事务写授权、事实决定、尝试、幂等回执和一条既有重算 outbox。Manager 用现有队列合并并重算，无模型也能推进；不会每补一行冷算全店。全 pending 不占用成功请求编号，来源恢复后同编号可重试；部分成功则缓存整批回执，剩余缺口等待新 run/input 再组成新批。取证后输入、人工决定或本地 feed 发生变化会 CAS 拒绝整批。当前原 feed 已有价始终优先，adapter 不覆盖它。

原 H0 和已存原文件不修改。adapter 只在相同原成员、SKU、公司、原始日和数量仍一致且仍缺价时注入 unit/quantity，交原引擎计价。`3.335` 不在事实层改成 `3.34`；100 个数量 1 的同价组件保留 raw 总成本 `333.5`，100 个 `0.004` 保留 `0.4`。既有引擎仍在指标/报表节点合计处到分；单个 `3.335` 在该原有边界显示 `3.34`，这不等于逐单先舍入后累计。

部分已有成本不一律转人工：若原缺价行有唯一内部成员，而同一平台成员的独立普通已价 sibling 能在完整来源库存中证明，只补该缺价行，已有贡献保持原值。只有部分总额、无法定位组件或单位的，继续 `partial_cost_component_inventory_incomplete`。已人工决定、已价、ERP 冻结、身份冲突、未展开组合单位换算继续保留待核。

补发不借用人工商品成本清单：v2 对原始已封存 pricing 行生成独立 component key/context。必须有唯一补发关系，并额外读取原销售订单；仅同店、已发货正常原单、唯一同 SKU 普通成员、原公司/原日/原数量单位一致且原平台父子成员明确时才采用。多候选、原成员缺失或公司日期不符均不广播父单证据。实际成本仍由原补发规则计入原引擎决定的账期，不按取价日或采集日迁账。

adapter 标记事实批准的账期，原 calculate 使用它自己已经求出的真实 posting period 检查授权。旧五月授权不能把事实自动用到六月；模型或来源变化产生另一个账期的缺价时，需要该开放期的独立 v2 授权。原 v1 和普通源成本没有此内部标记，处理规则保持原样。

已核实原商品成本由既有退货规则在另一月冲回时，属于原价格事实的下游依赖，不能按事实月份裁掉其证据。该月封存的实际 `cost_return` 原订单/SKU会把对应原报价 SHA纳入自身 run proof；不把同店其他无关订单或月份的报价全量纳入。

事实实际采用的报价原件会绑定首份不可变 run proof 和原始 SHA；重新 seal 无法替换已绑定原件。人工撤销追加记录并进既有重算队列，adapter 去掉该来源贡献；同上下文在重新批准 v2 前不会自动重采纳。已结店月拒绝采用或撤销事实，已结和已确认实发继续由统一 Checker 与现有冻结层保护。
