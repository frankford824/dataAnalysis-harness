# 有限订单前缀与店月就绪

`ledger_feed_boundary.v1` 只能由本机 Manager/OrderFeed 产生。Manager 把本次持久 pending 的来源序号绑定到内部 context；文件任务没有来源序号时只捕获一次当时的全局头。OrderFeed 在同一个 SQLite 读事务保存 snapshot、所需前缀、已消费前缀和确认的上游店铺映射。没有内部任务 context 的人工核算继续要求读事务当时的全局头。HTTP/模型不能提交或覆盖这些字段。

核算保存 `feed_boundary` 到既有 run proof/等价验证。Checker 和 Workspace.close_period 使用同一个验证器：所需前缀已被真实消费、snapshot 相同、映射未变、没有来源错误；本店后续会计实体或无法证明归属的会计实体仍阻断，直到核算重新验证。其它店的全局序号不进入本店已证明结果的金融输入身份。旧结果缺少新证明时继续走全局同步的保守逻辑。新格式不合法、源码身份改变、源回退、映射变化均不能取得就绪。

结账预览按已认证人工、请求编号、月份及选定店铺集合保全一次技术边界。尚未追平时不生成财务预览或业务授权，重试同一请求沿用同一前缀；改操作人或范围必须使用新请求。追平后，边界进入原有签名预览，确认沿用它并继续验证每店金融输入、来源变更、权限及结账保护。技术等待记录不能当作财务批准或完成。

这个合同证明的是“截至已捕获前缀”的结果，不声称读取了未来持续增长的全局尾部。已观察到的本店后续变化仍会阻断旧结果。需要新的截至边界时发起新预览；不能把后续序号当成已经处理过。

取证上下文另按 sealed 原始行依赖识别：原始 native/cost/date 证据仍在当前活动槽位时，添加不相关公司资料不改变它；移除、替换目标原件仍改变上下文。金融总额/公摊改变仍影响财务CAS，原件缓存的重验复用由 source recovery 的当前尝试处理，不放行旧Worker租约。
