# 7 月读取与核算修复（2026-09-24）

本次合并 7 月读取/核算、提成汇总展示和对账重复流水修复。发布使用版本/文件哈希门禁与自动回退。
既有已结账指针、人工核定实发与原始证据不变；未结账结果按新规则重新生成。

## 对账重复流水与提成展示

- 对账事件按店铺、支付渠道隔离，不再因为别的模板缺少流水号而降低去重键。未发生的金额方向只在比对键上统一空值与零；原金额不改。
- 微信支付流水和支付宝账务流水使用经核对的事件标识；微信过户转账的收、支两条腿分别保留。同订单不同流水号、不同到账时间、分笔收款不按订单号合并。
- 无逐笔支付标识的账单使用完整复合键跨文件比较，保留单表真实重复次数。缺少安全去重依据、同一事件金额/订单冲突或流水号精度丢失时保留证据并拦截；不猜测长编号、不静默选金额。
- 去重统计在店铺账期页显示，并明确统计是全部已上传源表范围，不是当前月份的入账金额。原文件及物理行号可追溯。
- 流水身份风险同时进入结账与核定实发约束，编辑窗口提前显示；不能人工勾选忽略后晚些时候才发现无法核定。
- 提成所有汇总维度及导出补齐个人托管销售额、已有兼职分摊、利润额（扣兼职）。未知不显示成零，人员筛选不重新分摊。店铺合计与其中个人/托管明细有明确口径，不重复相加；核定实发不改。

真实只读审计覆盖 43 店、206 份当前对账文件、2,668,930 行。皇莉诗三份微信原表 20,747 行去重后 16,859 行，排除 3,888 行重复，8 月 5,064 行完整保留。
科学计数法丢失流水号精度（抖店 luckywish、浅花涧、喜必顺）及抖店烘焙旧表截断运单编号仍需原始导出佐证；系统不伪造修复源数据。

## 已实现

- 共享表未知或冲突店铺不再回退当前计算店铺。未确定金额不入账，保留原行、待核提示和结账拦截。
- 代发表的店铺/付款日期互换，仅在有效日期和唯一登记店名双向验证通过时恢复解析位置。原文件与物理行号不变，逐行记录转换依据。
- NAS 支持模型声明的精确目录别名（刷单、补单），不采用模糊路由。失败文件 5 分钟后重试；财务接收错误纳入错误接口与日志。
- 归档目录重复接收改为幂等处理，旧路径保留迁移记录。同名替换先保存旧内容的哈希归档。
- 共享输入变更会触及已有账期但没有独立文件槽位的店铺。
- 京东两级表头费用明细、新版抖音保费、缺少未使用列的拼多多订单表可以识别。京东交易汇总不与同簿费用明细重复入账。
- 空表与有充分依据的辅助页不再造成误阻塞。无表头费用不能仅按 sheet 名忽略；只有与正式明细逐字段吻合的副本才排除。
- 推广控制池身份随投影传递，按自身范围回写进账贡献，包括零控制总数的冲回。未知月份控制表不再摊到所有历史月份，相关费用/利润保留待核。
- 新增按店/账期/指标的源贡献与投影金额一致性门禁；差异超过 1 分或出现非有限金额时不发布新结果。
- 订单台输入以实际数据内容而非全局同步水位标识。新增有界进程内计算前复用：包含完整归一数据、模型/代码版本、提成/配置/人工成本版本和同步状态；每次命中验证当前 run 与证据校验和。dirty/unknown 版本禁用，任何实质输入变化都会重新计算。
- 解析缓存保留来源识别语境、工作表月份与当前文件名，重命名不无谓重解，也不混用不同来源语境。
