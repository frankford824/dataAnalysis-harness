# 经营分析与月度工作台合同

经营口径版本：`operations-20261027.v2`。本服务读取保存的财务结果和证据，不改损益模型、提成基数、已核定金额或冻结账。

## 金额与归属

- 到账销售收入＝未扣退款的对账销售收入－销售退款；1688 已保存的“销售收入”本身是含负售后退款的净额，必须先经独立来源证据识别，不能再冒称未扣退款收入。退款率只在原收款与退款均有可闭合证据时计算，以未扣退款收入为分母。
- 商品成本包含已有净商品成本（保留退货成本冲回）、补发和代发。商品毛利＝到账收入－商品成本。
- 推广只认 `n_ad`；本金佣金与客服打款归售后，不能再进入推广重复扣除。
- 利润＝到账收入－商品成本－推广－平台费用－发货运费－售后；利润额＝利润－兼职。
- 店铺兼职来自同月共享公摊决定，冻结后优先读取对应结账 run 的份额。个人按已认领做货的未扣退款销售收入分完整店铺份额，包含托管。筛选人员、托管或店铺不重新分摊。
- 做货参与者间按已保存的有效份额归属业务；抽点只展示提成参考与原提成，不加入业务合计。身份不明确的业务单列未认领。
- 托管、非托管互斥；未知分类保留，不混入任一分类。宝贝键为 `store_id:product_id`。
- 团队按当前组织版本分组，响应明确返回 `organization_mode=current_revision` 和版本。不能据此声称历史组织结构已经复原。
- 汇总率用汇总金额计算。缺少来源保持空值。环比/同比在零或负基数下只给金额差及明确说明，正基数才给变化比例。颜色只表示红升绿降。

## 接口

`operations_api.install(app, workspace_callable, model_callable)` 安装只读接口：

- `GET /api/operations/month`：`period`、`level=store|team|person|product|order`、`platform/store_id/team_id/person_id/product_id`、`managed=all|managed|standard`。订单必须先明确店铺。
- 同接口支持 `offset/limit`（最多 200）、`sort_key/sort_direction/sort_basis=current|mom|yoy`。分页不改变范围合计。
- `GET /api/operations/export.csv`：相同筛选与排序，忽略分页；`comparison=current|mom|yoy` 选择比较列。归属业绩与不累加的抽点参考有独立记录类型。
- `GET /api/operations/evidence`：店月必填，可按宝贝、主子订单和经营来源科目筛选，支持分页，返回原件 SHA、工作表、行号及分摊依据。
- 导出与证据接受 `expected_input_sha`；输入变动返回 409。响应包含口径版本、run 引用、输入与范围指纹；比较结果另绑定比较月份指纹。

`is_final` 不由有数字或 HTTP 成功推断。阶段、不完整证据、未处理的新资料以及个人归属缺口都不能冒充对应范围最终结果。

金额在后台汇总、比较和导出前不按行舍入到分；分币金额至少保留六位有效小数。逐单投影用十进制归集，范围汇总从内部原始精度求和。界面两位显示产生的尾差由 `display_rounding` 单列说明，CSV 的“全范围两位显示尾差（不计金额）”列同步解释；它不是补录或调账行。

公司默认店铺汇总读取已保存 statement，不展开全公司逐单表。详细维度按需读取，先用 Polars 把 metric×order 长表缩成订单宽表；缓存有界且随输入、组织、模型、决定及制品版本失效。

## 经营投影与兼容

`Slice.operations_evidence` 在人员扩展前保存每个指标的一次订单贡献；`capture_projection()` 保留订单/宝贝身份。服务调用 `keep_projection(ws, run_id, slice)` 写入并校验封存 `<run>.operations.parquet`。已审核且实际入账的逐单补录也追加同一份实际贡献。

旧 run 没有完整经营投影时，店铺保存金额继续可看；缺失的商品或个人分项保持空值，不使用提成比例或全店均摊补造。整期人工总额与原始投影的差额保留在待归属层。

月度工作状态、决定卡片与批量结账由 `/api/automation` 提供。客户端不从 `can_close` 重建状态；决定与结账均先预览、再按输入与提案指纹确认。所有写操作使用真实人工会话，服务身份不代替财务决定。

## 1688 收入证据合同

1688 的 `trade_receipt_1688` 把“订单收入”和负“订单售后退款”合入保存净额。`income_evidence[store_id]` 公开 `operations-income-1688.v1` 来源合同、原收款/退款/净额及 proof；逐单映射与诊断不公开为大对象，也不因是否展开明细改变输入身份。

独立已知净额必须来自选定真实 run 的已保存结果（已结且有核定覆层时使用该覆层），并满足：`n_receipt` 明确 available；`calculation_inputs.metric_totals.trade_receipt_1688` 与其闭合；四个其他退款指标均明确不适用；来源模板捕获证明或有效封存原 facts 属于受信 1688 收款合同。`proof.net_source.result_sha` 为 `{store_id,period,run_id,platform,statement_receipt:{id,value,available}}` 的 canonical SHA，不能由调用者提供 known_net 替代。发布读回需独立对照真实保存结果。

原收款/退款拆分只允许 `settlement / alibaba1688_settlement_in_v1 / trade_receipt_1688` 的 counted contribution，按确切 subject “订单收入”/“订单售后退款”区分。正负只校验方向，不用于猜分类。封存与已有 manifest SHA、原件锚、范围和净额必须闭合；未知 subject、原 facts 缺失或矛盾时，原收款、退款与退款率保持空值，已独立证明的净额仍可保留。商品/订单层还须通过同 run 的封存投影、link 与实际 factor 闭合；人员层在已证明归属上分配，不能凭提成比例反造来源。

公司及店铺兼职继续使用后端既有共享公摊决定或冻结份额，不按新经营 gross 收入重摊全公司。个人兼职只以可证明的、含托管且未扣退款做货销售收入分配完整店铺份额；缺少 gross 权重时保持未知，店铺实际费用仍保留。

需后续业务裁决但本轮不追改：1688 原共享公摊收入基数可能沿用已净的旧 `n_receipt`，与新个人 gross 权重不同；原退款按已有保存账期/结算日期保留，因此当期退款率不是同一销售批次的终身退款率。跨月退款重归与历史工资/实发政策须另行明确，经营看板不会静默改写。

## 一次决定与跨月范围

营业范围默认仅本月；选择“持续生效”必须明确业务起止月。自动处理规则从后端 `/api/automation/rule-contracts` 取得固定名称、业务说明和合同 SHA，界面只展示业务说明，不允许编辑规则金额逻辑或合同版本。授权明确一店一规则、业务月份与带时区执行有效期，再以预览/确认 CAS 保存。全局规则开关未启用时明确显示只保存授权，不声称已自动执行。

本月适用的范围与授权历史来自后端 `policies[]`，状态、过期与版本变化均由后端判定。前端不按日期重算权限，不因跨月显示重复发起批准。仅后台 `can_revoke` 允许时显示撤销按钮：先读取当前决定与输入 SHA，填写理由并预览，再以 CAS 确认。撤销保留历史；已冻结营业范围由后台拒绝撤销。规则授权可撤回后续执行权限，不重写历史金额。

专家页、店铺清单和总览每次读取时，在已缓存财务结果上刷新最终 `close_verification`；同月公司收入与兼职决定更新最终就绪及 ETag，不要求未变财务 run 重算。未定公司范围或兼职不能显示可结账。内部仅保留建议金额所需的精简费率依据，出站继续移除产品明细。

## 等待资料与维护

月进度的 `counts.waiting` 和决定区的 `waiting_groups` 直接取自后端。等待摘要显示缺少材料、跟进角色、起始时间、受影响店铺与交付提示；具体人员未配置时只显示“角色未配置”。资料类进入现有店月资料页，技术故障显示“已交维护”，不转成人工成本填报。等待不等于完成，资料或来源版本变化后由后端解除旧等待并继续处理，前端不自行隐藏或推断财务就绪。

专项入口测量只使用固定动作 `waiting_summary_open` / `waiting_deliver_open`、`operation_complete` / `observed`、内部店月和零观测耗时。不记录材料、原因、角色、姓名、handoff正文；它只是入口访问，不证明已补齐资料、人工实际工时或财务核定。多店组进入公司资料总览，不逐店发 N 条事件。

## 测量与验证

人工操作测量通过 `/api/automation/telemetry` 最多 50 条批量发送，只含随机会话/事件 ID、固定动作、内部范围、次数与耗时，不读取金额输入值、姓名、订单或请求响应体。登录后发送，失败不阻断业务。服务耗时不等于完整人工工时；80% 减少目标须固定真实样本另行测量。

前端默认 `pnpm test` 执行 `test:unit` 和 `test:browser`；CI 可分别调用以避免重复。浏览器环境初次需 `pnpm exec playwright install chromium`。

浏览器门禁实际等待全部 HTML 场景 PASS，任何 FAIL、超时、页面错误均非零退出。另起临时 HTTP 服务，验证真实会话、决定、经营导出/下钻、测量，以及专家页最终结账阻断、一次人工授权跨业务月、合成 XLSX 原件＋冻结 ERP＋真实 Manager/service 的批量月结闭包。合成原件测试不能代替批准的历史实账黄金验收。截图和临时数据位于系统临时目录，不写入仓库。
