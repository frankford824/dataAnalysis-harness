# 台账稳定性审查与整改方案

审查基线为 `ca30b27463c717401c22798a0cb0e3bb426ae763`，提交范围为洛杉矶时间 2026 年 9 月 26 日 00:00 至 10 月 26 日 23:59。审查覆盖近月台账改动、验收与回放、服务核算入口、发布保护和前端验证入口。本轮只新增审查材料；验证在临时源码副本和临时工作区中执行，未连接生产数据库、未发布版本、未调整生产金额或账期。

结论：近期问题分布在身份与生命周期、分摊粒度、证据完整性、时间版本、异步追平和业务展示六类。54 次提交全部伴随测试文件改动，不能归因为没有写测试。新增局部测试没有代替全量合同验证；最近的取价准入变化与旧测试预期已经冲突。当前主要缺口是：真实业务验收存在未裁决失败，部分判定逻辑会漏报，历史回放没有覆盖现行服务完整路径，发布入口没有强制绑定业务验收收据。

整改的产品目标按用户进一步说明修订为：稳定地自动完成日常台账任务，减少人工核对、反复解释口径和持续开发介入。身份匹配、数值关联、规则版本及证据检查属于系统内部职责。默认页面只呈现已完成的业务结果、正在自动处理的进度，或一项确实需要业务决定的事项；不能把更多核对表、开关和异常数字当作交付完成。

采用现成 Agent 运行时来推动业务任务：自动读取已授权来源、查找和补充证据、调用既有核算工具、定位差异、执行已批准规则允许的处理、复核并输出结果。只有资料无法自动取得、业务规则确实冲突或必须由业务授权的决定才提交人工；需说明具体问题、候选处理及影响，避免要求用户自己研究技术口径。确定性核算与 Checker 是内部执行基础，不应转化为额外的用户操作。

运行时可以减少模型调用、工具循环、会话和任务推进的自写编排；现有验收器漏洞需要先修，使自动执行具有可靠的完成判定。该整改的目的在于让系统能够承担业务工作，工程诊断助手只是辅助能力。

## 已确认的验收漏洞

### G1 对账结果可能错误地报告零差异

位置：[accept.py](/home/wsfwk/dataAnalysis/ledger/tools/accept.py:377)。临时探针替换输入与计算结果，只验证验收器本身，复现：

- 人工利润为 100，实际利润为 999，分项收入不变时，`run_case()` 返回 0。原因是未登记为已解释差异的毛利和利润没有纳入失败判定；避免重复累计差异金额不应取消派生公式断言。
- 预期有金额的指标不存在或 `available=False` 时，跳过比较，返回值仍可为 0。
- 结果同时包含 5 月与 6 月时，只取排序后的第一个切片作人工账比较；后一个月金额错误不影响返回值。`Case` 没有显式目标账期合同。

独立的可结账测试可能捕捉某些缺失状态，因此不能说整组测试必然全部漏报；可以确认的是“零差异”这一对账结论本身并不充分。

完成标准：必需指标和人工对照列缺失必须失败；每个验收案例显式绑定店铺、月份及规则；毛利和利润独立验证公式与预期值；所有选定店期被比较，遗漏计数必须为 0。以上三个反例均必须被验收器拒绝。

### G2 对账命令行差异非零也返回成功

位置：[accept.py](/home/wsfwk/dataAnalysis/ledger/tools/accept.py:290)。`main()` 输出结果后无条件 `return 0`。探针让 `run_case()` 返回 123.45，入口仍返回 0。pytest 外层有断言，能拦住相应失败，但直接运行脚本的自动化只检查退出码时不能拦住。

完成标准：通过返回 0；非零未解释差异返回非零；NaN、无案例、缺材料或缺必需输出返回明确失败。命令行和 pytest 必须使用同一份判定结果。

### G3 历史回放没有运行现行服务的完整核算路径

对照 [replay.snapshot](/home/wsfwk/dataAnalysis/ledger/ledger/replay.py:176) 与 [service](/home/wsfwk/dataAnalysis/ledger/ledger/service.py:391)：回放使用 XLSX 的 `ingest → run → slice_dict`，提成调用 `commission.compute`；现行服务还接入订单台快照、流水人工确认、人工成本补录、Registry 新版人员关系和 `commission_engine.calculate`，并保存留档与发布结果。

回放已包含逐人的旧版提成比较，不能说它完全不检查人员金额。确切缺口是：这些比较没有覆盖现行服务新增的输入与提成执行路径。局部服务测试已存在，但没有与真实材料及发布前后业务比较形成统一整链收据。

完成标准：在临时 Workspace 和 Registry 中调用现行服务入口，纳入固定版本的文件、订单台快照、人员关系、人工确认和补录；从服务产出的 run 验证明细、报表、提成、API 和导出。只改变人员关系、补录或上游身份时，对应结果变化必须被发现；不相关店期应保持不变。

### G4 正式基线的身份和范围不够严格

[基线文件](/home/wsfwk/dataAnalysis/ledger/tests/baseline/statements.json:2) 实际标为 `90ae2b8-dirty`，目前覆盖 6 家店、6 个店期，月份为 2026-05 和 2026-06；最后修改提交为 2026-08-26 的 `cb87a83`。本地语料中没有文件的现用平台不会由“所有有语料店铺均被覆盖”检查发现。

[write_baseline](/home/wsfwk/dataAnalysis/ledger/ledger/replay.py:273) 可以写入 dirty 或 unknown；[CLI](/home/wsfwk/dataAnalysis/ledger/ledger/cli.py:449) 对 dirty 只警告，使用 `--store --record` 也会把当前子集直接写成整份基线。正式记录中没有文件 SHA 清单、规则摘要、订单台快照身份、人员版本和人工决策版本的完整绑定。探针已成功写入 dirty 基线，但仅写在临时目录。

完成标准：正式基线拒绝 dirty、unknown 及未声明的范围缩减；包含完整代码 SHA、规则 SHA、原始材料清单、上游 manifest/水位、Registry 和人工决策版本、覆盖范围及批准依据。旧基线保留；每条预期变化先裁决后登记，不允许为消除红灯直接覆盖。

### G5 数值比较把金额容差用于比例

位置：[replay._walk](/home/wsfwk/dataAnalysis/ledger/ledger/replay.py:335)。所有数值共用 0.005 的绝对容差。探针把覆盖率从 0.949 改为 0.952，比较器仍报告 clean。若完整结果中的可结账布尔值同时变化，其他字段可能会捕捉；这里确认的是比例字段本身会漏报。

完成标准：金额、比例、计数、标识和布尔值分别声明比较规则；金额按原始精度和批准的舍入规则比较，比例按比例精度，计数和标识精确一致。0、未知、未核定不能互相等同。拒绝非预期 NaN/Infinity。

### G6 发布保护没有强制绑定业务验收结果

[打包入口](/home/wsfwk/dataAnalysis/tools/deploy/package-ledger-release.py:16) 和 [部署入口](/home/wsfwk/dataAnalysis/tools/deploy/win/deploy-commission.ps1:15) 校验提交、预期版本、文件 SHA、备份及启动版本；这些应保留。[发布前后保护](/home/wsfwk/dataAnalysis/tools/verify-ledger-release.py:25) 比较已结账结果和已核定记录的不可变性。

上述入口没有强制要求与待发布提交、模型及材料版本绑定的业务验收收据。历史保护通过不能单独证明未结账金额、当前成本完整性、新版提成或导出正确。仓库外可能有人工检查，本轮没有取得每次历史发布的执行收据，不能推断过去发布都没有检查。

完成标准：打包和发布都校验同一收据；收据缺失、版本不符、材料变化、必需测试未运行、任何必需用例 skipped/xfail、未裁决差异非零时拒绝放行。发布后的当前业务回读与历史不可变检查分别签发结果。

### G7 浏览器检查未接入默认测试命令

[package.json](/home/wsfwk/dataAnalysis/ledger/web/package.json:10) 的 test 脚本只执行 Node `*.test.js`。仓库另有 8 个 HTML 浏览器用例，本轮未发现该目录的浏览器自动执行配置。HTML 用例内存在模拟 fetch，适合验证展示与交互，但也不能替代真实服务合同验证。

完成标准：对成本缺口与补录、利润构成、冻结值与最新试算、筛选后导出、快速切换与迟到响应建立可自动执行的浏览器检查；以临时服务和固定 run 作为数据来源，页面与下载比较同一版本；失败自动使发布门禁非零退出。现有 Node 测试继续保留。

### G8 成本口径变更后旧断言仍按原口径运行

快速回归中已有失败在带有精确提交版本印的隔离副本中定向复现。`4680bd0` 删除 `ORDER_DAY_COST_SOURCES` 中的 `register/register_first`，说明通用库存时间戳不能证明历史有效期；[历史取价测试](/home/wsfwk/dataAnalysis/ledger/tests/test_taobao_douyin_history.py:15) 仍把这两类来源标为可以入账，[组件隔离测试](/home/wsfwk/dataAnalysis/ledger/tests/test_order_components.py:83) 也用 register 构造其应正常计价的对照行。结果是 4 个参数化取价测试和 1 个组件测试失败。

可以确认的是代码合同与测试预期冲突；仅凭这些失败，不能判断应恢复旧取价政策。组件隔离仍正确保留坏行与正常行的隔离标记，该测试最后一步被独立的价格来源规则拒绝，并不证明隔离器误伤了正常行。

完成标准：先登记并核对取价政策的业务依据、适用平台/月份及来源证明要求；再让正例提供充分证明、反例保留不充分证据。全量快速回归通过且不得重新接受未经证明的参考价；所有改变准入或金额的规则变更必须有影响清单和相应样本预期，不能只跑新增测试。

## 整改次序与交付标准

“修复一个问题”必须同时给出来源、受影响范围、修复前后差异及反例；最终收束由下表判定。各阶段先在离线副本实施，生产历史修正另行审计。

| 阶段 | 产物 | 明确完成标准 | 主要责任 |
| --- | --- | --- | --- |
| A 修复验收器 | 统一判定结果、退出码和字段比较合同 | 本轮 7 个探针均按预期拒绝错误；全部必需快速回归通过，且原本正确样本仍通过；缺字段、缺月、缺语料和空覆盖均失败 | 工程维护者，财务确认必需指标 |
| B 重建可解释基线 | 真实样本包、完整输入 manifest、差异裁决表 | 当前 11 项真实语料失败及 5 项快速回归冲突逐项有来源证据及结论；不得用放宽阈值、补零或直接重录消除失败；每个现用平台至少一个完整店期，跨月业务覆盖相邻账期；没有样本的平台明确不在已验收范围 | 财务和业务确认口径，工程提供逐行证据 |

| D 将验收变成发布要求 | 与代码、规则、输入身份绑定的门禁收据 | 无收据不能打包；收据换 SHA、换输入或少跑任一必需用例均被拒绝；历史冻结保护与当前业务回读分别通过；在临时环境完成回滚和重启演练 | 发布维护者 |
| E 观察业务稳定性 | 连续完整结算周期的缺陷与差异记录 | 建议连续两个完整结算周期没有未解释金额差异或同类金额错误复发；异常能被系统提前识别并给出处置依据；允许保留的缺口按已批准规则标记范围和影响 | 使用人员与财务，工程跟踪 |

阶段 B 的平台范围以当前启用的业务配置与本次发布目标为准，不能只限于已经拥有样本的五个常见电商平台。没有独立期望值的样本不能被称为黄金样本。人工 Excel 的旧公式、外链及缓存需要核对；对账双方共用解析器时，应另有独立行数与控制总额，防止同时漏行而相互对平。

阶段 C 必须覆盖下列交叉情形：

- 身份：拆单、合单、作废父行、同 SKU 多条真实发货、跨店同号；provided/required/historical 三种成本策略。
- 费用：同运单不同真实费用、重复导出、正负费用、跨月退费、全零分摊基数、缺失与冲突基数；逐原始费用与逐目标金额守恒。
- 成本：整单缺价、部分组件缺价、合法零成本、参考价与历史价、上游补证到达、旧整单补录遇到部分真实成本、补发与原销售月。
- 时间：流水发生月与订单月、来源切换、旧 run 与最新试算、结账后晚到资料、人员关系生效边界；不得覆盖已冻结金额。
- 执行：冷算与复用一致、文件和上游同时更新、重启、任务接收失败后重试、持续更新不饿死文件核算、失败后旧结果仍可用且状态明确。
- 展示：单人、多人与店铺范围；未知与真实零；已入账与完整成本；同 run 下主表、明细、利润构成与导出相符。

已有 `recompute_reuse` 包含完整输入和 Registry/人工版本，并在命中时校验留档；现有冻结、审计和守恒测试也应继续复用。整改重点是把这些机制串成强制的可复现业务验收，不新增另一套金额引擎或重复调度器。

## Agent SDK 建议

### 可以采纳的部分

采用现成 Agent 运行时，负责模型调用、工具循环、会话和事件流，可以减少自行编写的 Agent 编排。首个目标应是一店一月的业务执行助手：自动收集资料、补证、调用核算、处理已批准规则内的异常并复核完成；工程稳定性助手承担后台定位与测试，不作为用户需要日常操作的另一套系统。

账务侧继续保留一个小而明确的案例状态和检查结果：`待检查 → 检查中 → 待材料/待业务确认/失败/已验证`。模型结束回复不等于案例已验证；独立 Checker 根据必需检查、版本和差异判定是否完成。正式入账、重算发布、结账、历史更正及实发核定沿用现有确定性接口与授权。

### 最小试点与通过标准

只读试点工具提供：读取固定案例、查询已授权来源并把补充证据放入临时材料包、追溯原始行、读取差异、在临时副本中应用已批准规则和执行核算、查询任务、取得 Checker 收据及输出业务结果。工具按案例 ID 固定店铺、月份和输入版本。生产写入和结账不在本次试点授权范围内；后续自动执行通过现有业务接口及明确的规则授权接入。通用 shell 与任意 SQL 不作为业务助手的日常工具。

首次任务和恢复任务均使用同一权限模板；任务与每次工具调用保存参数摘要、输入身份、结果状态、证据位置、错误及重试次数。使用工具实际返回值作证据，模型推理文本不能代替执行收据。长任务返回持久任务 ID，由现有工作队列管理；宿主实现取消、超时、次数及费用上限，不把它们假设成两种 SDK 共有的同名参数。

建议离线试点固定 20 个案例：六类风险各 2 个，共 12 个；工具超时、重复触发、恢复后工具配置、越权访问、格式错误结果、来源过期、缺失材料和模型停服各 1 个，共 8 个。每个案例预先标定正确证据、应调用能力和最终状态，验证标准为：

1. 20 个案例的必需检查执行率 100%；其中证据足够、规则已批准的案例必须全部自动完成，不要求用户逐笔选择匹配关系或理解技术口径。
2. 缺资料案例先自动调用已授权来源补证；确实不能解决的，输出一项可理解、可直接决定的业务问题，不能把整套核对流程转交用户。
3. 证据编号与来源摘要一致率 100%，不编造金额或“已完成”结论。
4. 所有确定性失败均保留失败或待处理状态，错误结果被误判为已验证的次数为 0。
5. 所有生产写入和越界工具请求被宿主拒绝；重复或恢复任务不会额外创建业务动作。
6. 同一输入使用新旧运行时得到相同 Checker 结果；模型不可用时仍能手动运行确定性核算与验收。
7. 每例耗时、工具次数、重试和成本均有记录并满足试点前设定的上限；没有实测前不承诺节省比例。

先完成阶段 A 和 B，得到可信验收器与材料，再评估这个试点。以同一批任务记录改造前后的人工操作次数、人工处理时间、自动正确完成率和开发介入次数；证据充分的试点任务人工操作必须降至零，其他任务的人工负担必须下降，不能通过隐藏差异或跳过检查达成。若 SDK 只让同样不完整的验收更快地执行，它会放大错误的完成感。成功标准是证据完整、状态正确和工程维护量减少，不能以对话回复看起来合理作为通过。
