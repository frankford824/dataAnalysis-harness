# 拼多多平台问题核查与修复

## 核查范围

依据用户提供的 `PDD问题/pdd平台店铺典型问题汇总.docx`、8 份关联 TXT 和此前截图。文档的段落、表格、10 张嵌入图片均已逐项读取。TXT 共 666 行，涉及 659 个不同订单号。核算试验扩大到模型中全部 17 家未归档拼多多店铺。

用户确认的规则：订单关联的收入、退款、平台费、赔付、商品成本、补发成本、运费等按原下单日归集；蓝旗订单商品成本为零；成本采用下单日历史价，缺少历史依据另行核价。该日期调整仅适用于拼多多，不改变其它平台的退款归属。

## 根因及处理

| 问题 | 处理 |
| --- | --- |
| 用结算日、退款日或补发单创建日决定月份 | 拼多多订单关联指标采用原订单日期。保留原始发生日及行号用于核对 |
| 合单导出把主单上的多单号列表写到每个商品行 | 订单台快照改用商品行的原平台订单号；API、快照、台账使用相同身份 |
| 蓝旗未进入采集变更判断和成本输入 | 采集哈希、API、快照、台账都保留旗帜，蓝旗不计商品成本；旗帜清除能触发更新 |
| 实际金额为零的退款行消失 | 保留原表确实填写为零的退款记录；空金额不伪装为零 |
| 用当前价、缓存参考价冒充历史成本 | 按原下单日和成本所属公司查历史区间；缺价显示待核价 |
| 套餐展开后多个组件共享一个内部商品行号，逐行保存互相覆盖 | 先按原内部商品行归组，再按组件数量和历史单价计算总成本 |
| 浏览器套餐折叠偏好影响成本采集 | 订单成本请求明确要求展开原组件，仅覆盖该次请求的选项 |
| 缺价默认为零，利润和提成仍能出数 | 独立保存待核价明细，相关汇总不出金额，阻止提成计算和结账；支持搜索、分页及导出 |
| 接口读取异常返回空成本列表 | 错误返回失败状态；界面保留错误及重试入口，切单不会沿用上一单数据 |
| 商品编码含斜杠导致增量读取落到 HTML 页面 | 修正实体路径；目录事件作为目录指针消费，不为每条目录变更读取完整商品价格 |
| 补发时间被用于选择提成比例版本 | 台账保留原下单月份；无法核实原下单时刻时不套用补发时刻的比例 |
| 缺价后重复抓取相同订单详情 | 保存原组件及订单版本；订单未变化时复用原组件，只重查历史价；版本变化才重新取原单 |
| 历史发布脚本重放旧价格修复过程 | 已安装历史取价规则后，不再重放会恢复当前参考价的旧迁移 |

- 三个反馈店铺使用生产输入文件及冻结的订单台数据进行隔离重算。666 行 TXT 均找到相应记录，未发现已入账金额归错月份，计算报错为 0。
- 17 家未归档拼多多店铺均完成隔离核算，已入账订单关联记录的月份检查为 0 异常。
- 台账非慢速测试 1141 项通过，14 项慢速测试未运行；随后补发原时刻保护的相关 66 项测试通过。
- 订单台历史取价及原有合同检查 8 项通过；离线 HTTP 检查 3 项通过。
- 订单台数据库测试在独立临时 schema 和单一事务中运行，覆盖历史价、组件汇总、蓝旗、冻结保护、审计和增量事件；结束后整体回滚，确认 schema 不存在。
