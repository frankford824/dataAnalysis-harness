## 当前判定

本轮已实施稳定性门禁、月度自动化、经营看板、主动补证及受控运维代码。**工程检查点不等于上线完成。** 真实财务样本、运费正式采纳、人工工作量与实际月结观察要分别判断；不能拿合成测试、模型回答或部署成功代替。

当前仍未达到上线标准，不签发合格发布收据，不执行生产部署。最终候选提交的完整检查保存在 `artifacts/ledger-automation-20261027/final-<提交短SHA>/attempt.json`；失败尝试保留原身份，不拼接不同提交的报告。

生产侧本轮只做原件、已发布元数据及严格只读查询；没有提交、重算、反结账、更正金额、核定实发或执行部署。原始附件的 SHA 保持不变。工作副本、完整日志与财务明细留在受控私有目录，不随源码交付。

## 已确认的根因与对应治理

| 根因 | 已确认问题 | 实施的治理 |
|---|---|---|
| 身份与生命周期 | 平台、内部订单、原销售成员及补发成员不能混用；原主单证据不能广播给全部成员 | 明确实体命名空间，按原成员、SKU、公司、原日与原数量取证，矛盾保留待核 |
| 粒度和聚合 | 同运单跨主单、重复收费、退费与组聚合不等同逐费目标；逐单舍入会改变总额 | 保留原收费与实际包裹，按约定精度聚合；无法归因的逐费差额不编造 |
| 证据完整 | 参考价或带日期 JSON 不能自动当历史价；有报价不等于原数量及原销售成员已证明 | 受信源只读历史查询，原件和上下文绑定，未知不补零，源冲突不择一猜测 |
| 账期与版本 | 结账时收入池会变化；当前版本标签不能证明实际代码一致 | 店月输入/血缘摘要，完整源码 SHA、批准收据与启动基线；变更使旧预览失效 |
| 异步与恢复 | 接收、排队、写档、租约、重试可能发生在不同阶段 | 同事务回执/outbox、幂等键、认领令牌、续租和过期执行隔离，沿现有队列恢复 |
| 展示范围 | 费用、退款、未认领、托管、抽点及个人工资存在不同用途与口径 | 单一后端经营指标源，范围和输入身份随明细/导出传递；未知与真实零分开 |

另有两项实际发布风险已关闭：旧全量发布脚本绕过验收并可能覆盖生产模型；只比提交号又会漏掉生产源文件漂移。本轮捕获实际部署代码 124 份，与其版本标签对应 Git 提交存在 22 路径差异，已逐项审查兼容。发布改为实际源文件前置清单、同一收据、备份恢复验证、停止全部所属写进程、发布后真实入口回读。

## 历史兼职分摊：只读候选，不改历史

已实际采集五个月份及 57 店账期头。138 个已结店月中，85 个具有真实冻结份额（6 月 42、7 月 43）；另 53 个旧月缺少可用冻结金额，不能用当前重摊值代替历史原值。

已知冻结额与当前候选存在 79 项差异（6 月 41、7 月 38）。这只是候选差异，不能直接称为少发或原收入必错。精确只读查询进一步核验 85 个计算模型与结账配置日志，总额均支持与当前同额；不能再把差异笼统归为总额版本未知。

84/85 个当时收入池逐分复现原冻结（6 月 41、7 月 43）；余下 1 个存在同秒运行顺序歧义，保留不可判定。7 月 38 个当时分母小于当前可见分母，变化来自已有店保存收入值的后续变化，不能概括为后来新增店。历史与当前运行同时存在原件集合及引擎标识变化，6 月还伴随模型版本变化；这些证明基准不同，不证明原始业务收入哪一版正确。当前两月仍各有 8 店收入未知，完整最终分母不能假定。

新的关闭路径必须在应处理范围、收入依据和公司兼职总额确定后冻结同一基准。已结与已核定实发继续保护。

**2026-10-27 业务决定已确认：先保全历史并列清单，本次只自动处理新月。** 本次不包含历史差额补扣、补发、跨月结转或历史积压自动入账；候选差异保留只读，不作为历史错账判定。首批新账期由上线范围与人工规则授权明确，不预设为 10 月或 11 月，不因服务器月份变化自动扩大。历史样本仍用于隔离回归，不因退出历史自动处理范围而从验收中删除。

这项决定只更新业务范围文档，未改变运行时代码和生产设置。完整八组执行证据仍属于 `8ba3b651f30e57334b2af269ccdcf1cd14693fa6`，本次文档更新不生成新的合格发布收据，其余真实财务、源补证、人工基线和实际周期门槛继续保留。

本轮运行时发现也作了身份区分：只读账号不能访问维护账号的 Python base 路径，不代表生产解释器损坏。现有维护连接已只读验证服务 Python 为 3.12.10；发布脚本同时识别 Windows venv 启动器与其真实 base 子进程，不会把仍在运行的写进程遗漏后就捕获静态快照。

## 运费试验的证据边界

首轮只有费用原件与 ERP H0，不能当作当前完整业务路径的结论。后续已主动取回当前活动范围 619 份唯一原件、697 个槽位，约 1.97 GB，逐 SHA 校验；没有向用户索要原系统中已存在的资料，也没有按文件名月份直接筛掉未知文件。

完整固定输入下，7、8 月分别保留全部 198,064 / 275,533 条原收费，同一原生产引擎与 v6 包裹规则均实际运行。费用条数、绝对金额、正费用/退费、原规则重放计入、实际目标分摊及严格 ERP 权重覆盖必须分别报告。

v6 包裹成员最终权重来源是 ERP `line_amount`；`native_item` 是身份粒度，不能据此说金额来自平台。单一目标直接归属、全零等分、被忽略成员及当前 ERP 负向分摊另列，不能混称 ERP 精确比例或已证明历史冲回。

原规则投影存在多原收费聚合到同一 link 的情形。原组金额可以核验，但没有逐费血缘时，逐费目标金额及差额必须为空。实验包装器不能靠线性重建后补尾差伪造“原引擎实际逐笔分配”。利润影响只有目标身份、原始日期和原账期规则都证明时才能模拟，不能用收费月份补记账月份。

完整来源审计、共同范围、独立守恒与可证明日期的最终结论以本轮私有封口报告为准。任何覆盖变化均不是自动补扣依据；本轮没有启用候选运费规则。

完整同源输入的绝对金额覆盖为：7 月 A 91.2624%、B_v6 90.6067%、严格 B_ERP 87.9980%；8 月 A 94.4033%、B_v6 93.7719%、严格 B_ERP 88.4480%。因此本批不支持直接全量替换正式运费规则。可归因范围、原组守恒、跨店候选及利润情景限制见 [运费 A/B 安全报告](freight_AB_20261027_safe.md)。

## 已落地的自动化与看板

- 统一 Checker、案件/尝试/决定/授权/回执，批量月结预览与确认；无法忽略硬阻断。
- 原生确定性关联与历史成本取证；模型关闭不妨碍已批准且证据充分的正常处理。
- 一份经营指标服务覆盖公司、团队、个人、店铺、宝贝与订单；同范围导出绑定同输入身份。
- 1688 只有原始科目证明拆分时才展示毛收入与退款；否则保留已证明净收入，拆分项和相应个人权重待补齐。
- 抽点参考不重复加入做货业绩；未认领保留；托管互斥汇总；个人兼职按已确认的归属销售权重处理。
- 月度工作台集中展示真实剩余事项，缺资料和技术维护分组；资料到达使旧等待失效，但不假报财务完成。
- 登录操作员与独立服务身份，所有变更请求经过认证；服务不能替人签署月结、实发或规则授权。

成本源事实 v2 已实现并通过实际 Manager/引擎一致性回归：保存受信原始报价并交原引擎按既有聚合精度核算，不把多位小数硬塞人工两位补录接口，不改 v1 授权，不改原 H0、已结或实发。合成案例中，100 项缺口引用同一报价、一次批次写入和一次派发，总共初算及补证后重算两次；人工补录表保持为空。`100 × 3.335` 按原精度形成 333.5，不能逐行先舍入成 334。普通与部分已定价成员、可证明原成员的补发及证据不足分支分别验证。生产启用仍需独立服务身份及人工批准的范围授权，不能由模型自行批准。

模型候选能伪造可写 JUnit、退出零码或借整个工作树读取受保护数据，所以这些都不能作为修复证明。现模型检查只拿白名单代码投影；真正验证由持有隐藏预期的父进程在独立断网子进程外核验实际结果。金融 oracle 进一步检查真实服务链的 SQLite、原 proof、封存原件、完整范围及冻结层。缺真实案例或其它完整门禁仍阻断，不用一项金融测试冒充八项发布门禁。

实际 token 已记录，但没有供应商报价或已结账单，人民币费用保持未知，不能拿公开模型标价冒充此网关的实际费率。调试中断时的在途未知 usage 也单列，不算免费。
