# 订单金额核对（台账读取）

合同保持 `ledger-feed.v1`，按合同版本检查兼容性，不因 `engine_version` 升级停消费。
不重置 checkpoint，不改 `controls.paid_amount` 或快照旧列含义，不改上游采集及账单解析。

## 核对入口

`GET /api/order-feed/alignment/{store_id}?order_key=原订单号或平台子订单号或支付关联号`

从台账已接收的快照和增量读取，返回读取时的 `snapshot_id`、`consumed_seq` 和订单组。
不会为了这次查询推进同步、写入账目或反结账。新增字段未回填的旧单可能仍为未知；
新代码上线本身不会让没有变更事件的历史订单获得新字段。

- 单号按 `online_order_keys` 展开，处理冒号及末尾 `,coid`，兼容旧快照的 `online_order_no`。
- 子订单号和支付关联号用于查找。支付号按字符串保留前导零；同一支付号不作为合并订单或去重流水的依据。
- 仅在同一个已确认映射的店铺内，将线上订单键相交的内部订单合组；每个内部订单头只累计一次。
- 汇总 ERP 应付、已收、优惠、运费。任一成员该字段未知时，汇总也为 `null`，不能显示为零。
- 含明确未付款、已收为零或货到付款的订单，返回 `receipt_check=not_applicable`，不据此判断漏收。
- 其他组返回 `requires_statement`，表示需要平台订单明细和资金流水核对，不表示漏单或金额不符。
- 不检查 ERP 货品 ID、类型的暂时空缺，不按套餐配件行对平台宝贝单价。

金额是十进制字符串；前端应将 `null` 显示为“待核对”或“—”。ERP 当前应付不等于平台
买家付款，也不保证永远等于商家收入，尤其是拆合单、售后改价及不同时点的资料。
优惠不一致不能直接判为漏采。平台券与支付渠道拆分继续读取台账已有第 1、3 层资料。

## 增量兼容

旧快照合并实时实体时，显式保留新增列，防止按旧 schema 投影将新数据丢弃。
旧快照的 `orders.paid_amount` 仅作为 ERP 应付别名读取，`settled_amount` 仅作为 ERP 已收别名。
商品付款全空或部分未知时，读取汇总保留未知。现有引擎 `buyer_paid` 兼容角色不代表
经过平台确认的实际付款；新增核对入口明确标记 `amount_basis=erp`，不由此产生收入分录。
