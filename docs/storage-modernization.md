# 台账存储治理

## 共享证据

calculation.model_json/rules_json 新记录保存 $ledger_snapshot_v1 内容哈希引用，原始UTF-8字节压缩保存在同库 evidence_blob。SHA-256覆盖未压缩原文，读取校验解压长度与哈希。旧的内嵌JSON仍可读取。Registry.calculation_evidence还原原文；所有业务字段不变。证据表禁止修改和删除。

历史迁移只处理候选库，保留原库作为回退。候选库逐条比较逻辑证据摘要，停写后同步尾部及可变表，比较源库与候选库内容并执行完整性检查。禁止在在线库直接删除历史或去掉不可变触发器。

## 无变化的计算

同店同月的最新记录只有在输入指纹、引擎、业务结果一致且留档SHA-256通过时才复用。只忽略随机calculation_id，不忽略金额、规则版本、待核价或错误信息。旧留档没有校验文件时仍正常新算，文件缺失/损坏不会被复用掩盖。

## 持续增长控制（2026-10-19）

先部署兼容读取，再在 `storage-policy.json` 开启下列开关；默认关闭，不在服务启动时批量改写历史库。

- `compact_snapshots=true`：新 `run.result`、`calculation.summary_json` 及报表切片的大 JSON 使用同库、不可变、按内容寻址的 zlib 证据；小于 1024 字符的字段仍内嵌。保留原始 UTF-8 字节、全部金额及计算 ID，读取逐次校验长度和 SHA-256。存储表示变化不改变账期、结账引用或发放确认。
- `period_snapshot_reuse=true`：新输入指纹改用账期级完整结果、五类证据表（事实、待核价、成本覆盖缺口、分摊依据、订单问题）和逐行提成明细，以及引擎、模型、规则及其版本。其他账期变化不再单独导致本期另存一份。来源行、数量、零和金额变化、归属及规则变化仍导致新留档；缺失或损坏任一封存附件也不能复用。旧指纹首次过渡会正常产生一版新记录；dirty/unknown 引擎不启用账期指纹。
- `run_directory_bundles=true`：仅在 `archive_all_completed=true` 时生效。尚未发布的新核算附件写入唯一 NAS 目录，在本地只保留一个目录链接；逐文件校验封条和完整目录清单随附件保留，`storage.db` 记录一条目录归档。旧平铺文件及已发布目录不搬迁。目录准备失败则保留旧的本地写入流程；开始写入后 NAS 中断会使证据未就绪，不能用缺失成本或零金额代替。查询历史目录时不会因 NAS 不可用而转到空白本地路径。

Workspace 和 Registry 连接自动还原已知 JSON 列；SQL 在 JSON 函数中用 `snapshot_json(value)` 还原。只读运维脚本通过 `snapshot_store.install_reader(conn)` 注册读取支持，或显式 `resolve(conn, text)`；原始 SQLite 列现在可能是引用，不能直接将它当业务 JSON。旧内嵌记录照常读取，新开关也可以随时关闭以停止后续压缩/目录写入。**关闭开关不会移除新记录的读取要求，回退时必须保留兼容读取代码，禁止直接退回不识别引用的旧版本。**

这轮控制只影响后续写入，不会自动腾空既有大库。历史重编码及收缩仍须执行下述离线候选、逐条逻辑校验、停写追平和可回退切换流程。

原生索引器每批写入等待后台合并结束；有新索引、首次维护及每 120 次扫描时调用 Tantivy 引擎自己的垃圾回收。Windows 正在使用的映射文件计入 deferred 并在后续轮次重试，不按文件名前缀猜测删除；`index-gc-status.json` 和 `/storage` 记录最近结果。

## 运行要求

先部署共享证据写入，再构建候选库。停机补齐尾部及校验后才能原子切换；旧库备份保留。原始账单、已结账引用及审计记录不删除。平台同步合同和checkpoint不得因存储治理被重置。

## 冷数据分层

storage-policy.json启用维护后，默认保留最近两天、每店每月最新两版以及全部已结账引用在本地。其余已完成留档复制到配置的历史存储，校验SHA-256后以原子链接替换原文件。原路径、计算ID和账务记录不变；原路径可继续被旧版查询或导出读取。历史库不可访问时停止归档，不移除尚未校验的本地文件。

维护进程按小时运行，磁盘低水位时提前执行，单轮有文件数和字节预算。storage.db记录内容哈希和目标；/api/storage/status提供实际可用空间、归档进度与失败原因。历史存储应使用服务账号可访问的UNC路径，不依赖交互式盘符映射。

## 同步库和订单台基线

订单台计划任务 LedgerOrderSnapshot 每天 03:30 生成并验证 ledger-feed.v1 快照；沿用 OrderConsole 的运行身份。脚本在发布前保留前一份 manifest，使用独占锁避免重复执行，失败不写成功标记，不调用 prune。台账自然消费已验证的新基线，不修改消费断点。

同步库通过停写后的 compact-feed 转换为 auto_vacuum=INCREMENTAL。候选库逐表比较记录数及逻辑 SHA-256（含 feed_state），校验后才切换。维护线程每轮用有限时间回收空闲页。归档源快照时同时保留订单台当前 manifest 和台账正在消费 manifest 引用的对象。

## 运维和回退

- `D:\ledger\home\storage-policy.json` 控制启用、留热天数/版本数、每轮上限、低水位、NAS 目标及源快照目录。
- `D:\ledger\home\storage.db` 记录原路径、内容哈希和归档位置；历史文件通过原路径读取。目录逻辑大小会包含远端链接内容，判断 D 盘占用应查看磁盘实际可用空间。
- NAS 暂时不可用时停止迁出；历史导出依赖 NAS 恢复。不要清除 NAS 对象、改变共享权限或直接删链接。
- 迁移凭据和原库保存在 `C:\ledger-storage-migration\20260913`。旧库只作为迁移时点备份，恢复前必须处理切换后的新增记录，禁止直接覆盖在线库。
- 恢复某个冷文件：停止该文件的维护操作，根据 storage.db 找到目标，复制到原路径旁的临时文件，核对 SHA-256，再以原子替换恢复为本地文件；保留归档证据。
- 当前热数据和审计记录随业务正常增长；本方案消除重复快照和无变化重算增长，并将过期留档迁出，不删除账务历史。

2026-09-14 实施凭据：原提成库 44,911,292,416 字节压缩成 NAS 上 `migration-20260913-registry.db.gz`，6,621,153,780 字节。流式解压 SHA-256 为 `28658cb58e975361998ea3ea0816167702087e4967fb8943b17de1ce13007078`，与原库一致。C 盘原提成库副本及已用完的提成候选库已经移除，恢复时先按 `original-backup-archive.json` 找到 NAS 备份；不能再依赖旧的 C 盘原库路径。同步库原件仍保留在迁移目录。

## 全量 NAS 留档模式（2026-09-14）

按用户要求，生产已启用 `archive_all_completed=true`，替代原先“保留近两天、最新两版”的默认策略。已完成核算文件（含结账引用）、登记过的原始文件、固定输入副本、完整解析缓存，以及非活动源快照对象，可以校验后迁出；文件稳定 300 秒后进入队列。临时目录、未完成留档、主数据库和在用检索目录排除。

全量迁移用 `python -m ledger.storage_bulk --root D:\ledger\home --drain --workers 6`，不受日常每轮字节预算限制。单个对象校验后共享，原文件以原子链接替换；NAS 的 Windows sharing violation 会重试，仍占用的文件保留本地并延后处理，随后补迁。其他校验或网络错误会停止继续提交新任务。

日常策略每 600 秒执行，最多 5,000 份 / 4 GiB，3 个并发任务；低空间时提前执行。归档状态同时记录总量、完成量、剩余量、占用延后项和错误。`finished=true` 仅表示本轮结束，必须同时检查剩余量与错误；全量验收须再次扫描可迁移清单。

离线数据库备份和旧核查目录按整目录保留关联文件，逐文件校验后迁到 NAS `bundles/ledger`，原目录保留符号链接。发布锁 `D:\ledger\releases\ui-release.lock` 继续保留本地。当前任务使用中的目录及最近发布资料留在本地，运行程序、主库和在用检索目录不移到 SMB。
